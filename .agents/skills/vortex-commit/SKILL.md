# Vortex 提交流程

完成一次范围明确、经过验证且消息符合当前仓库规范的本地提交。用户明确要求提交才允许暂存或提交；Skill 自动激活、仅生成消息或讨论提交流程不构成提交授权。

## 1. 每次先读取当前规范

使用 `git rev-parse --show-toplevel` 定位仓库根目录。下文中的命令在该根目录运行，所有规范路径均相对仓库根目录解析，而不是相对 Skill 安装位置；不能因从子目录启动而漏读根目录规范。

在检查和提交前完整读取以下文件，不依赖旧对话或记忆：

- `AGENTS.md`，以及目标文件所在目录中适用的更具体 Agent 指令。
- `docs/engineering/git-workflow.md`：提交范围、标题类型、scope 和正文的唯一规则来源。
- `docs/engineering/testing.md`：按风险选择检查和区分产品/实验 Workspace。
- `docs/engineering/review-checklist.md`：选择本次相关 Review 项。

必需规范缺失或不可读时停止，报告路径；有无法解决的规范冲突时先向用户确认。不要在本 Skill 中另行维护消息格式、类型表、正文模板或测试命令副本。

## 2. 检查工作区、暂存区与提交范围

先查看分支、变更清单及暂存状态：

```bash
git status --short --branch
git diff --name-status
git diff --cached --name-status
```

根据用户当前任务确定目标，再读取相关的未暂存 diff、已暂存 diff 和拟提交的新文件内容；未跟踪文件不出现在普通 diff 中，不能漏掉新增模块或测试。

- 不默认整个工作区都是本次任务，不默认已有暂存都能提交。产品与 playground 是独立 Workspace，不因产品提交顺带纳入实验。
- 暂存区混入无关内容、同一文件混有不同目的改动，或任务范围无法确定时，先说明具体情况并请求方向。
- 未经用户授权不得取消或覆盖原有暂存。不要靠 `git commit` 的路径参数绕开混杂暂存区；在确认后的明确暂存集合上提交。
- 将多个独立目的拆分为单独提交；每个提交都重复最终暂存复核。没有可提交改动时报告并结束，不创建空提交。
- 如发现进行中的 merge/rebase 或未解决冲突，停止并说明；不要自行完成其他 Git 操作。

## 3. Review 与验证

按目标 diff 检查实现逻辑、文档一致性、遗漏的新文件、意外删除、构建产物和敏感内容。不要为了比对而主动读取本地 `.env` 或私钥；发现凭据、认证头或私密内容时停止，仅报告文件位置和风险，不复述敏感原文。

根据刚读取的测试规范执行与本次变更相称的只读检查：纯文档或 Skill 修改不机械运行完整 Rust 测试；产品检查不覆盖 playground，实验改动另行检查。

- Rust 检查优先使用 `--locked`；格式检查使用不改写源码的模式。需要更新锁文件、格式化或修复时停止并请求对应授权。
- 记录实际命令、结果及未检查项目；已有验证仅在对应内容未变化时复用。
- 存在阻断问题、敏感内容，或检查失败且用户本次未明确豁免时，不提交，给出问题与建议。
- 用户本次明确允许忽略某项检查时，只按其指定范围跳过或接受失败；消息与报告中注明例外，不能写成检查通过，也不沿用旧任务的豁免。
- 网络/权限限制导致检查无法完成时按当前工具审批流程处理；无法验证时明确报告，不擅自跳过检查或扩大执行权限。

`commit` 只授权提交已有改动，不授权修复、格式化、重写文档或配置。不修改检查失败涉及的代码来凑出一次“通过”的提交。

## 4. 生成消息、暂存与最终复核

从最终选定的实际改动生成消息，严格遵守当前 `docs/engineering/git-workflow.md` 的类型、scope、中文说明和正文要求。消息说明完成的变化，不把未来方案写成已实现，不重复敏感内容。

按明确的文件路径使用 `git add --` 暂存；不使用 `git add .`、`git add -A`，不强制加入被忽略的本地文件。需要精确选择部分改动而不能安全操作时，先请求用户处理暂存范围。

暂存后检查：

```bash
git diff --cached --name-status
git diff --cached --stat
git diff --cached
git diff --cached --check
```

确认整个暂存集合都属于本次授权、必要的新文件已包含、没有敏感内容，且与消息及验证范围一致。若暂存内容在检查后发生变化，重新 Review 和验证受影响部分，再生成消息。

## 5. 提交、核验与交接

提交前检查生效的 Git hooks；如果已知 hook 会改写源码或暂存区，先说明并请求对应授权，不擅自运行或绕过。

用户已经明确要求提交且范围/检查没有阻断时，执行普通本地 `git commit`，有正文时用独立的 `-m` 参数传入。遵守当前工具审批要求；不因使用 Skill 获得额外权限。

提交失败时读取错误并停止处理，不自动修复 hook、绕过检查或改变 Git 配置。若 hook 改写工作区或暂存内容，先报告并重新确认范围，不盲目重试。不得使用 `--no-verify`、`--amend` 或重写历史，除非用户另行明确授权。

提交后核验：

```bash
git log -1 --format=fuller --stat
git status --short
```

确认最新提交的消息和文件符合本次目的。向用户报告提交 hash、主题、实际验证结果/豁免及剩余未提交改动。不要把保留的无关改动说成工作区已干净。

不自动 push、创建 PR、切换分支或处理其他提交；这些需要独立请求。
