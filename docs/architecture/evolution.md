# 架构演进与模块拆分建议

本文基于 2026-10-27 源码提出后续建议，不是当前模块清单，不授权修改源码或新增 crate。
现状见 [逻辑模块](logical-modules.md)；功能候选与依赖见 [后续能力](../design/development-directions.md)。

## 判断依据

现有 crate 依赖方向已能隔离模型协议、工具和终端，优先在 crate 内整理职责。
Session、配置和 AppState 的变化原因逐渐增多，值得先划清内部边界；Provider 已完成
请求、选项、解码和传输拆分，应保持现有分层，避免为了对称再次抽象。

拆分依据是独立的变化原因、状态所有权和测试入口，不是文件总行数。多个文件包含
大量模块内测试，不能仅凭长度判断生产逻辑过大，也不为测试访问方便扩大公共 API。

## 第一优先：配置与 Session 内部边界

| 候选调整 | 当前集中之处 | 建议边界 | 保持不变的契约 |
| --- | --- | --- | --- |
| 配置内部拆分 | `config.rs` 同时包含 DTO/默认值、合并/验证、文件读取与项目路径检查 | 先分为配置模型、纯合并/验证、文件加载三个内部职责，原公开入口继续导出 | 优先级、整条替换、字段白名单、来源与安全错误 |
| Session 内部拆分 | `session.rs` 同时包含公共类型/句柄、通道构建、actor 循环和发布逻辑 | 分开公共连接/命令/事件与私有运行时；actor 继续独占历史及任务，通道与发布留在运行时边界 | start_session、send/recv、顺序、单 Turn、关闭与背压 |

先做等价移动，再考虑把 actor 局部变量收敛为私有状态类型；不要同时改并发模型或
历史提交策略。配置的文件 I/O 当前就在 Core，不能先在文档中假定已经移出。
是否另建配置 crate，需等第二个实际调用方或明确依赖问题出现后再评估。

## 第二优先：TUI 状态处理

`app.rs` 集中输入编辑、slash 分派、模型选择 pending、CoreEvent 投影与状态栏展示。
当这些职责继续增长时，先按“输入/命令处理”与“会话事件投影”拆私有处理函数或子模块，
保留唯一 `update` 分派入口和 AppState 所有权，避免控件自行发送异步业务命令。

Transcript 当前承担展示条目、Markdown 组装、滚动度量与绘制；先保留现有封装。
只有新增缓存、折叠或独立布局算法时，再将布局/视口职责从条目投影中提取。
不提前建立通用 Component、Screen、内部 event bus 或 renderer trait。

## 功能演进带来的新边界

| 触发条件 | 应增加或调整的职责 | 前提与限制 |
| --- | --- | --- |
| 加入 system prompt、项目指令或 Token 预算 | 独立上下文装配，分离指令、历史选择与 wire 转换 | 复用 [消息构建设计](../design/runtime/message-building.md)；不把 ContextAssembler 写成现有 API |
| exec 迁移 | CLI 增加 Session 事件的文本呈现，复用已有 Turn loop | 明确输出、错误和退出语义，不复制第二套工具循环 |
| 第二个文件工具 | 从 WorkspaceFs 中确认可复用的路径和句柄规则，增加有界读取 | 不把列目录授权扩大成读写授权，保持输出与数据外发边界 |
| 文件修改或 Shell | 引入权限决策、审批及进程隔离/取消边界 | 先设计并验证，再接入副作用；Linux 目标选型为 Bubblewrap，当前尚未实现 |
| 会话保存与恢复 | 建立事件存储、历史投影与恢复生命周期 | 当前 CoreEvent 并非完备日志，不能直接序列化就宣称可恢复 |
| 第二种模型协议或 MCP | 在已有 trait 下新增适配器并明确生命周期 | 不假定 SSE 载荷和思考历史语义一致，不预建空后端 |

DeepSeek 等接入的 Thinking 历史支持是协议与上下文契约变更，不能作为 UI 拆分的附带
修复；签名、opaque 状态和文本思考也不应强行统一为正文。

## 已落地的诊断边界与后续扩展

共享 `vortex-diagnostics` 已承接三个 HTTP 路径的请求关联、正文日志副本与后台错误预览，
CLI 仍管理 subscriber/文件；Core 与 TUI 没有新增诊断依赖。当前能力见
[诊断设计](../design/cross-cutting/diagnostics.md)，不是待创建的空模块。

后续在明确需要跨模块耗时、诊断报告或 OTel 导出时，可在该 crate 增加相应职责，
先明确业务关联 ID、隐私、资源预算及退出规则。当前没有这些能力，也未建立完整可观测性平台。
只裁剪 wire_trace，不把整个 crate 固定为 Debug 专用；若要 Release 正文诊断，另定显式
开关与验收，不悄悄开启 release debug-assertions。普通元数据事件无需统一绕行 WireTrace。

## 暂不拆为新 crate 的内容

- 通用事件/协议继续在 Core：出现独立使用方且运行时依赖确实造成负担后，再考虑协议 crate。
- 配置与模型管理先按内部模块整理，不因概念独立就增加发布和依赖单元。
- MCP 的具体归属在真实接入时决定；不要给当前 Tools 标注已经拥有 MCP client。
- Sandbox 保持“尚未接入”定位；出现真实后端后再确定它与权限策略的依赖，不提前
  在实际依赖图中画入 CLI/Tools → Sandbox。

## 实施次序与验收

建议先独立处理配置或 Session 的等价拆分，一次一个职责；再处理 TUI 的输入与事件投影。
新功能与行为变化另列方案，不与纯移动混在一起。实施前仍需作者明确授权。

重构验收应覆盖原公共导出、配置错误与优先级、事件 FIFO/终态、工具历史、Shutdown
背压、模型切换确认及草稿保护。先运行对应 crate 的离线测试，再按
[测试规范](../engineering/testing.md) 完成检查；本文件不构成任何测试通过记录。
源码移动后同步模块映射与链接，架构文档不保留已经失效的“当前文件位置”。
