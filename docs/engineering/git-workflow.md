# Git 协作规范

## Commit

- 每个提交只处理一个目的，不把功能、重构和无关格式化混在一起。
- 提交前检查暂存差异和敏感信息，并按 [`testing.md`](testing.md) 执行与改动风险相称的验证。
- `commit` 请求只授权提交已有改动，不授权修复或格式化；具体修改边界见根目录 [`AGENTS.md`](../../AGENTS.md)。
- 以下消息规则适用于后续提交，不要求重写历史提交。

### 标题格式

```text
<type>(<scope>): <动词开头的中文说明>
```

`type` 必填，使用下表中的小写英文类型；中文说明保持简短，明确描述实际改动。
`scope` 可选，省略时同时省略括号，例如 `docs: 补充搜索工具接入方案`。
填写时使用小写英文模块名称，例如 `cli`、`core`、`provider`、`tools`、`tui`。

| 类型 | 用途 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修复错误 |
| `refactor` | 重构，不改变预期行为 |
| `docs` | 修改文档 |
| `test` | 增加或调整测试 |
| `style` | 仅格式调整，不改变逻辑 |
| `build` | Cargo 依赖或构建配置变更 |
| `chore` | 不属于上述类型的其他维护工作 |

根据实际改动选择类型，不根据任务中的“实现”或“修改”等措辞判断。
多个独立目的优先拆分提交，不用笼统的类型掩盖不相关改动。

标题示例：

```text
feat(tools): 接入秘塔网页搜索 API
fix(provider): 修复流式工具调用 ID 的处理
refactor(provider): 拆分 OpenAI Chat 流式处理
docs: 补充搜索工具接入方案
```

### 正文要求

小改动可仅有标题。新增功能、非显然的修复、重构，以及涉及配置或兼容性的变更，
须增加正文，标题与正文之间空一行，使用以下模板：

```text
原因：为什么需要这次改动。

改动：
- 主要修改内容与关键设计取舍。

验证：实际执行的检查、结果及未验证项。

注意：兼容性、配置迁移、安全或费用影响；没有则省略。
```

正文重点说明改动原因与影响，不重复罗列 diff 中的文件。验证记录必须真实，未执行检查
时明确说明未执行；不能把预期结果或计划中的测试写成已经通过。

## Pull Request

Pull Request 应说明目标、关键设计、风险、测试命令与结果，并关联相关 issue。终端 UI 变化需附截图或录屏；权限、配置或 Provider 行为变化必须说明兼容性和安全影响。未验证的平台或场景应明确列出。

当前没有额外的分支命名约定；形成稳定工作流后再在本文件补充，避免提前建立没有实际用途的流程。
